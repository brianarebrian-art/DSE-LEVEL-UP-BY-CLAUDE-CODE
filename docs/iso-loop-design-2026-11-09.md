## 4. 開工前要答嘅問題（覆檢嗰日決定）

### Q1　8 秒要唔要強制？

睇 §7.2 條 curve：

- 剷鎖之後正確率**冇跌** → 強制等待冇證據支持，框架卡應該**隨時撳得走**。
- **有跌** → 一個短嘅強制停頓可以係「改個形態」嘅候選，但要寫低憑邊個數字。

### Q2　A/B 比較乜？

| | 設計甲（建議） | 設計乙 |
|---|---|---|
| A 組 | 自診 → 同構題 | 維持現狀（冇卡、冇題） |
| B 組 | 自診 → 框架卡 → 同構題 | 自診 → 框架卡 → 同構題 |
| 量度緊 | 框架卡本身有冇用 | 成個閉環有冇用 |
| 主指標 | 同構題第一次作答正確率（即時、兩組都有） | 之後同課題正確率（`dse_topic_stats`，慢、噪音大） |

建議甲：兩組都有同構題，先有同一把尺去比。

### Q3　同構題計唔計入 `score`／`total`？

建議**唔計**，分開記（例如每節加 `iso: { shown, correct }`）。
計入嘅話 §7.2 條 curve 同 §7.1 嘅題數定義都會郁。
⚠️ `dse_progress` 係已批准嘅上雲 key，但喺入面**加欄**算唔算要重新批准，
§16.E 第 6 條只講 key —— 要創辦人講清楚。

### Q4　分組點記？

| 做法 | 好處 | 代價 |
|---|---|---|
| **甲：由 id 決定**，`hash(穩定用戶 id ＋ 實驗名) mod 2`，唔儲存，分析時重算 | 冇新增上雲數據；換機都係同一組 | 客戶端要攞到同 `getSyncUserId()` 一致嘅 id。⚠️ Better Auth backend 下 `session.user.id` ≠ Google `accountId`（見 `lib/auth/server.ts`），hash 錯 id 會令切換 backend 嗰日成批人換組 |
| **乙：每節記 `arm`** 入 `dse_progress` | 簡單，分析直接讀 | 同 Q3 一樣係喺已批 key 加欄；如果本機隨機分組，換機可能換組 |

未登入學生冇雲端數據，**點都計唔到**：可以照樣分組畀佢哋用，但唔入分析。

### Q5　同構題點揀？

建議題目加一個 **optional** `archetype` 欄（§6：optional 唔會令現有題目失效），
由學科首席經審題流程填（§12：機器唔可以自己判定兩條題同構然後推畀學生）。
**冇標記嘅題目唔觸發閉環，兩組一樣。** 同構題只由已審題庫抽，唔即場生成。

### Q6　框架卡內容由邊度嚟？

要一張**人手審**嘅「題目 `topic` → 卡片」對應表，或者卡片加 `questionTopics` 欄。
實驗範圍建議：只喺「有已簽卡 ＋ 有 `archetype` 標記」嘅題目觸發，兩組同一範圍 ——
否則 B 組好多時冇卡可出，會同 A 組無分別，稀釋結果。

### Q7　要幾多樣本？

以設計甲、主指標同構題正確率為例：假設由 70% 升到 80%（**純舉例，唔係實測**），
α＝0.05、power 0.8，每組約 **300 條**同構題作答；
同一個學生會答好多條，彼此有相關，實際要多過呢個數。

每週可用量 ＝ `retention.mts` §② 逐週 `questions × (1 − accuracy)`（即答錯條數）
× 「有卡 ＋ 有標記」嘅覆蓋率 × 每節上限 3 條嘅折扣。
**覆蓋率係瓶頸** —— 按第 3 節嘅數，而家大部分科目係零。

## 5. 無論點揀都唔變嘅約束
