# 計劃書：量度「學生有沒有做完、有沒有再練」（草稿，未批准）

**狀態：只是計劃書。沒有寫程式、沒有建資料表、沒有收集任何新資料。**
**依據：** 創辦人回覆 37b（2026-10-08）。起因是 2026-10-08 創辦人日報建議記錄五種匿名動作。
**要批准的是：** 第四節的方案。批准後，第七節的步驟才會開始；在此之前不會收集任何新資料。

---

## 一、想答的問題

| 問題 | 日報建議的名稱 |
|---|---|
| 有多少節練習開始了？ | `practice_started` |
| 開始了的，有多少做完？（即憲章 §7.1 的「中途離開率」） | `question_answered`、`session_completed` |
| 答完之後，有多少人打開解析？ | `analysis_viewed` |
| 做完一節之後，有多少人接着再練？ | `next_practice_started` |

## 二、現在已經有的資料（全部唯讀可查）

| 資料 | 涵蓋誰 | 答到甚麼 | 答不到甚麼 |
|---|---|---|---|
| `user_progress` 裏的完成紀錄（`dse_progress`） | 只有登入學生 | 做完了多少節、每節幾題、答對多少 | 中途離開的節完全沒有紀錄 |
| `dse_active_session`（同步上雲的未完成練習） | 只有登入學生 | 每個帳戶**最近一節**是否未完成 | 之前放棄過多少次 |
| `user_sessions` | 只有登入學生 | 每日有沒有打開網站 | 有沒有做題 |
| `session_feedback` | 所有人（匿名） | 做完一節後兩條問題的答案 | 沒做完的人不會見到問題 |
| Vercel Web Analytics | 所有人（只計總數，無 cookie） | 每頁瀏覽量 | ⬜ 待驗證：2026-10-08 以 Vercel API 查詢，回覆「Web Analytics not found」；網站有載入其程式，但數據是否真的有收集，需創辦人登入 Vercel 網頁的 Analytics 分頁確認 |

2026-10-08 用現有資料計算 §7.1 的結果（總數已寫入 Notion）：舊計法只計做完的節，所以量不到中途離開；最近一節未完成的登入帳戶有 17 個，只是下限。

**結論：** 未登入的學生（大多數）完全看不到；登入學生也只看到「做完的」。

## 三、可選做法

| 做法 | 新增資料 | 涵蓋 | 優點 | 缺點 |
|---|---|---|---|---|
| **甲** 只用 Vercel 頁面瀏覽量：比較練習頁和結果頁的瀏覽次數 | 無 | 所有人 | 不用改程式、不用改私隱政策 | 要先確認 Vercel 有數；重新整理頁面、直接開結果頁都會令數字失準；量不到解析和再練 |
| **乙** 2026-09-16 的提案：在登入學生的完成紀錄加兩個整數（原定題數、上次完成後放棄了幾節） | 兩個整數，附在現有同步紀錄 | 只有登入學生 | 不用開新表；可分清「做完 5 題卷」和「10 題做 5 題就走」 | 從未完成過一節的學生永遠量不到；未登入學生量不到 |
| **丙** 匿名計數：開始一節、完成一節時各送一次「某科 +1」 | 一張新表，只有日期、科目、動作、數目 | 所有人 | 最接近日報的五個數字；沒有任何身份資料 | 要開新表（migration）、新 API、改私隱政策；每節多兩次伺服器請求 |

## 四、建議：先做甲的確認，再做丙；乙暫不做

1. **先確認甲**（不用批准，創辦人自己看）：登入 Vercel → 項目 → Analytics。如果有數，練習頁對結果頁的比例可以馬上作為粗略參考。
2. **丙的設計**（要批准）：

   | 項目 | 內容 |
   |---|---|
   | 記錄的動作 | 只有兩個：「開始」（第一題出現時）和「完成」（去到結果頁時） |
   | 每次送出的內容 | 日期、科目、動作；「完成」另加兩個整數：答了幾題、打開了幾次解析；「開始」另加一個是非：是否從結果頁的「再練」按鈕開始 |
   | **不會**記錄 | 帳戶、電郵、IP、裝置編號、cookie、題目、答案、對錯、時間戳記（只記日期） |
   | 儲存方式 | 每日每科每種動作一行，只存累計數目，不存逐次紀錄，所以無法還原任何一個人做過甚麼 |
   | 權限 | 與 `session_feedback` 相同：只經伺服器寫入；學生和登入用戶都沒有讀寫權；RLS 開啟、不設 policy |
   | 防亂送 | 沿用 `proxy.ts` 現有的每個 IP 限速（只在記憶體，不儲存 IP） |
   | 學生看得到嗎 | 看不到。任何頁面都不顯示這些數字，亦不准出現「你放棄了 N 次」一類字眼（與憲章 §7「不做連續打卡」同一條線） |

   這樣可以計出日報的五個數字：開始數、完成數（及中途離開率）、每節平均打開解析次數、從結果頁再練的比例。題目報錯率已有 `question_reports`。

3. **乙暫不做**：丙已涵蓋登入和未登入學生；乙只多答「從未完成過」以外的一小部分，卻要改同步資料的格式。

## 五、私隱

- 丙收集的不是個人資料：沒有任何欄位可以指向一個人，而且只存每日累計數目。
- 但私隱政策現在寫「未登入的話，資料庫沒有任何一行是關於你的」。丙的計數不是關於某一個人，這句仍然成立；不過為了透明，建議私隱頁加一段，說明「我們會數每日有多少節練習開始和完成，只有總數」。
- 是否需要提高私隱政策版本號（會令登入學生再被問一次同意，見憲章 §7.2.1 的 2026-10-02 先例），要創辦人決定。
- 對外公布數字時沿用最小分母原則：某科某日數目太小時不單獨列出，免得百分比本身識別到人。

## 六、成本

- 每節多兩次伺服器請求。按現時用量（改制後約一個月，登入學生完成了 157 節；未登入的不明），在 Vercel 和 Supabase 的免費額度內，⬜ 待驗證實際額度。
- 不加任何套件，不用第三方分析服務。

**未做，等創辦人：**

1. **私隱頁與版本號（與 40a 有衝突）。** 40a 選了「私隱頁加說明，但不用登入學生再撳一次同意」。但現有規則（`lib/__tests__/privacy-consent.test.mts`）要求私隱頁文字一改就要提高 `POLICY_VERSION`，而版本一提高，登入學生就會再見到同意視窗。之前三次新增匿名資料（Vercel 瀏覽量、報錯、完卷兩條問題）都有提高版本。提出 40a 時漏看了這條規則，已向創辦人更正並再問。
2. **「打開解析」怎樣算。** 答題後解析會自動出現第一步；學生可撳「睇埋成個解析」或「下一步」看完整版，選了「以後直接睇晒」的學生則不用撳。所以數撳掣次數會少計這批學生。待創辦人決定是否數、怎樣數；決定前資料表沒有這一欄（migration 仍未套用，可以再改）。
3. **套用 migration**，並同日開啟 `PRACTICE_COUNTS_ENABLED`、更新私隱頁。

**每週唯讀計算**（開啟後使用，只把總數寫入 Notion）：

```sql
select
  sum(sessions) filter (where event = 'started')                       as started,
  sum(sessions) filter (where event = 'started' and from_result)       as started_from_result,
  sum(sessions) filter (where event = 'completed')                     as completed,
  sum(answered) filter (where event = 'completed')                     as questions_in_completed_sets
from practice_counts
where day >= (now() at time zone 'Asia/Hong_Kong')::date - 6;
```

中途離開率 ≈ 1 − 完成 ÷ 開始。某科某日數目太小時不單獨列出（最小分母原則）。
