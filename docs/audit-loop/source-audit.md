\#\#\# 2.1 手機（Mobile）所有問題（按嚴重程度排序）

\*\*問題 1：浮動按鈕遮蓋內容\*\*  
\- \*\*具體現象\*\*：喺 390px 闊嘅手機螢幕上，右下角嘅圓形浮動按鈕（情緒支援/無障礙）直接覆蓋正文中嘅文字。喺首頁底部覆蓋「✓ 全部功能免費」嘅文字；喺 Dashboard 頁覆蓋「...之後想幾...」嘅文字；喺 About 頁覆蓋第二張卡片嘅正文。  
\- \*\*對用戶嘅影響\*\*：學生喺手機閱讀時，關鍵文字被擋住，需要左右滑動或者縮放先睇到——喺搭車、排隊嘅情境下，呢個直接令學生放棄閱讀。  
\- \*\*點解不可接受\*\*：一個以手機為主要使用場景嘅平台，有任何 UI 元素遮蓋正文，係基本設計常識嘅缺失。呢個唔係「小瑕疵」，係功能障礙。  
\- \*\*具體改法\*\*：將浮動按鈕嘅 CSS \`position: fixed\` 改為喺內容底部加 \`padding-bottom: 80px\`，或者將浮動按鈕移至 bottom nav bar 旁邊嘅固定 slot，確保唔 overlap 任何內容。

\*\*問題 2：底部導航欄截斷內容\*\*  
\- \*\*具體現象\*\*：多個頁面（Dashboard、About、Subjects）底部內容被固定嘅 bottom nav bar（練習/進度/收藏/帳戶）截斷，最後一行文字直接被 nav bar 蓋住。  
\- \*\*對用戶嘅影響\*\*：學生睇唔到完整內容，尤其係 footer 嘅免責聲明同聯絡資訊。  
\- \*\*點解不可接受\*\*：固定底部導航欄嘅頁面必須加 \`padding-bottom\` 留位，呢個係前端開發嘅基本功。  
\- \*\*具體改法\*\*：\`body { padding-bottom: 64px; }\`（64px \= bottom nav 高度），或者用 \`scroll-padding-bottom\`。

\*\*問題 3：「加到主畫面」橫幅侵佔首屏空間\*\*  
\- \*\*具體現象\*\*：首頁頂部嘅「想快啲打開？可以加到主畫面」橫幅佔據約 60-80px 嘅垂直空間，喺 390x844 嘅螢幕上，呢個直接推低 owl mascot 同 hero heading，令首屏嘅核心 CTA（揀一科開始）被推到接近摺疊位。  
\- \*\*對用戶嘅影響\*\*：學生第一眼睇到嘅唔係價值主張，而係一個 PWA 推廣橫幅。3 秒建立信任嘅窗口被浪費咗。  
\- \*\*點解不可接受\*\*：PWA 安裝提示應該喺用戶已經體驗過產品價值之後先出現，唔係喺佢第一次打開就彈出嚟擋住核心內容。  
\- \*\*具體改法\*\*：用 \`beforeinstallprompt\` event 延遲顯示，改為喺用戶完成至少一節練習後先顯示。或者將橫幅移至頁面底部，唔好擋住 hero。

\*\*問題 4：手機練習頁三欄佈局崩塌\*\*  
\- \*\*具體現象\*\*：Desktop 練習頁係三欄（左：呢一題 context，中：題目，右：解析），但喺 390px 手機上，呢個三欄佈局要垂直堆疊，令「呢一題」嘅課題分類資訊、題目本身、同埋答錯後嘅解析之間需要大量滾動。  
\- \*\*對用戶嘅影響\*\*：答錯後要向下滾動先揀到錯因，再向下滾動先睇到解析——多層摩擦。  
\- \*\*點解不可接受\*\*：手機用戶嘅注意力極短，每多一次滾動就流失一部分用戶。  
\- \*\*具體改法\*\*：手機版應該將「呢一題」context 收起為可展開嘅 accordion，題目居中全寬，答錯後用 bottom sheet（從底部滑出）顯示錯因選擇同解析，唔使滾動。

\*\*問題 5：情緒彈窗打斷答題節奏\*\*  
\- \*\*具體現象\*\*：答錯題後，先要揀錯因（3 個按鈕），然後彈出一個「而家感覺點？」嘅全屏 modal，要學生揀「我 OK / 有啲失落 / 好慌」或者「略過」。  
\- \*\*對用戶嘅影響\*\*：中六生喺有限時間內做 10 題 MC，每題答錯就要經歷兩次彈窗，呢個係極大嘅認知負擔同時間浪費。  
\- \*\*點解不可接受\*\*：呢個功能嘅初衷可能係好嘅（關注學生情緒），但喺練習 flow 入面彈 modal 係反 UX 嘅。學生要嘅係即刻睇到點解錯、正確答案係咩，唔係被問「你開唔開心」。  
\- \*\*具體改法\*\*：將情緒記錄移至每節練習結束時嘅 summary 頁面，一次過問。練習中途絕對唔好彈 modal。或者改為題目卡片底部嘅一個細小 emoji bar（一撳即記錄，唔彈窗）。

\*\*問題 6：手機無法快速切換科目\*\*  
\- \*\*具體現象\*\*：手機版首頁只有 4 個科目快速按鈕（數學/英文/中文/公民），要揀其他科目要撳「揀其他科目（共 25 科）」再跳轉到 subjects 頁面，然後喺一個長列表入面搵。  
\- \*\*對用戶嘅影響\*\*：考 5-6 科嘅學生，每次切換科目都要 2-3 步導航。  
\- \*\*點解不可接受\*\*：手機用戶嘅導航應該係一個 tap 就到。  
\- \*\*具體改法\*\*：首頁快速按鈕改為水平滾動嘅 chip row，顯示最近練習嘅科目 \+ 「更多」按鈕。或者 bottom nav 嘅「練習」tab 直接展開科目選擇 sheet。

\*\*問題 7：字體大小喺小螢幕上偏小\*\*  
\- \*\*具體現象\*\*：題目正文同選項文字喺 390px 螢幕上字級偏小（約 14-15px），Footer 免責聲明更細（約 10-12px）。  
\- \*\*對用戶嘅影響\*\*：喺搭車、光線不足嘅環境下，學生需要放大先睇到題目。  
\- \*\*點解不可接受\*\*：DSE 考生嘅主要使用場景就係手機，題目文字最少要 16px。  
\- \*\*具體改法\*\*：題目正文 \`font-size: 17px\`，選項 \`font-size: 16px\`，footer 免責聲明最少 \`13px\`。

\#\#\# 2.2 iPad 或 Laptop（中型裝置）所有問題（按嚴重程度排序）

\*\*問題 1：側邊欄收縮為純圖標但無 tooltip\*\*  
\- \*\*具體現象\*\*：喺 1024px 闊度下，左側導航欄收縮為純圖標模式，但圖標冇 tooltip 或者 \`title\` attribute。只有 owl mascot 同幾個唔明顯嘅圖標。  
\- \*\*對用戶嘅影響\*\*：學生唔知道每個圖標代表咩功能，要靠記憶或者試撳。  
\- \*\*點解不可接受\*\*：Icon-only navigation without tooltips 係可訪問性嘅基本失敗。  
\- \*\*具體改法\*\*：加 \`title\` attribute 或者 hover/focus 時顯示 tooltip。或者喺 1024px 保持展開嘅文字標籤。

\*\*問題 2：內容區域浪費大量水平空間\*\*  
\- \*\*具體現象\*\*：喺 1024px 螢幕上，主內容仍然居中喺一條約 600-700px 嘅窄柱入面，兩邊係大面積空白。  
\- \*\*對用戶嘅影響\*\*：學生喺 13-14 吋 laptop 上溫習，螢幕空間寶貴，但內容區域只用到約 60% 嘅寬度。  
\- \*\*點解不可接受\*\*：中型裝置應該充分利用螢幕，例如用兩欄佈局（左：題目，右：解析），而唔係將所有嘢塞喺中間一條窄柱。  
\- \*\*具體改法\*\*：喺 \`md\` breakpoint（≥768px）啟用兩欄佈局，內容 \`max-width: 900px\`，左右 \`padding\` 減至 \`24px\`。

\*\*問題 3：練習頁三欄佈局喺中型裝置上太擠\*\*  
\- \*\*具體現象\*\*：Desktop 練習頁嘅三欄（context \+ question \+ feedback）喺 1024px 闊度下變得非常擠逼，每欄只有約 300px，題目文字同解析都要頻繁換行。  
\- \*\*對用戶嘅影響\*\*：閱讀體驗差，數學公式同長解析換行混亂。  
\- \*\*點解不可接受\*\*：三欄佈局只適合 ≥1440px 嘅大螢幕，中型裝置應該降為兩欄。  
\- \*\*具體改法\*\*：喺 768-1280px 之間改為兩欄（題目 \+ 解析），context 信息收為題目上方嘅 tag。≥1280px 先啟用三欄。

\*\*問題 4：科目網格喺中型裝置上排列不均\*\*  
\- \*\*具體現象\*\*：25 個科目卡片喺 1024px 闊度下用 4 欄網格排列，最後一行只有 1 個卡片，右邊 3 個位置全空。  
\- \*\*對用戶嘅影響\*\*：視覺上不均衡，感覺未完成。  
\- \*\*點解不可接受\*\*：呢個係小問題但反映設計者冇認真處理邊界情況。  
\- \*\*具體改法\*\*：最後一行嘅卡片 \`justify-self: center\`，或者用 CSS Grid 嘅 \`auto-fill\` \+ \`minmax\` 自動排列。

\*\*問題 5：多任務情境下無法快速切換功能\*\*  
\- \*\*具體現象\*\*：學生喺 laptop 上可能同時開住筆記 app，想喺練習、收藏、進度之間切換，但每次切換都要經過左側欄嘅導航，而且無快捷鍵。  
\- \*\*對用戶嘅影響\*\*：多任務情境下效率低。  
\- \*\*點解不可接受\*\*：中型裝置嘅用戶通常係認真溫習模式，應該有快捷鍵支援。  
\- \*\*具體改法\*\*：加 \`Cmd/Ctrl \+ 1-9\` 快捷鍵切換主要頁面。練習頁已有快捷鍵（1-4 揀答案、Shift+F 專注燈），應該延伸到全局導航。

\#\#\# 2.3 電腦或 Desktop（大型裝置）所有問題（按嚴重程度排序）

\*\*問題 1：內容嚴重浪費 1920px 螢幕空間\*\*

\- \*\*對用戶嘅影響\*\*：Desktop 用戶嘅生產力優勢完全冇被利用。  
\- \*\*點解不可接受\*\*：一個認真嘅溫習工具，應該喺大螢幕上提供更強大嘅功能，而唔係只係手機版放大。  
\- \*\*具體改法\*\*：加 Cmd+K command palette 快速跳轉科目/頁面。練習頁右側加即時 stats panel（今日正確率、時間趨勢）。加 split view 支援一邊睇解析一邊做下一題。

\- \*\*具體現象\*\*：Footer 用 3 欄排列，但喺 1920px 下呢 3 欄只佔中間約 600px，左右大量空白。  
\- \*\*對用戶嘅影響\*\*：Footer 連結密集排列喺窄柱入面，點擊區域細。  
\- \*\*點解不可接受\*\*：大螢幕 footer 應該展開為 4-5 欄。  
\- \*\*具體改法\*\*：\`grid-template-columns: repeat(auto-fit, minmax(200px, 1fr))\`，令 footer 喺大螢幕上自動展開。

\*\*問題 5：首頁盲測黑題 demo 喺大螢幕上太細\*\*  
\- \*\*具體現象\*\*：首頁嘅「盲測黑題」demo（由圓外一點 P 引兩條切線...）喺 1920px 螢幕上只佔中間約 400px 闊，幾何圖形同文字都好細。

\- \*\*點解不可接受\*\*：呢個 demo 係證明「掌握邏輯唔係背答案」嘅最佳展示，應該喺大螢幕上更加突出。  
\- \*\*具體改法\*\*：≥1440px 時將盲測 demo 改為 hero section 嘅右半部分，加大幾何圖形同文字。

\#\# 3\. 跨裝置共通嘅致命問題

\*\*致命問題 1：零分享機制、零增長引擎\*\*  
\- \*\*具體現象\*\*：全站冇任何 share button、social media link、referral mechanism。冇 Instagram、Threads、WhatsApp、Telegram 連結。Privacy policy 提到「一個學生自發嘅 Instagram 群組」但網站上搵唔到連結。冇「分享俾同學」按鈕。  
\- \*\*對用戶嘅影響\*\*：學生就算覺得好用，都冇便捷嘅方式分享俾同學。產品完全依賴口耳相傳，但連口耳相傳嘅種子都冇播。  
\- \*\*點解不可接受\*\*：一個以「口碑」為目標嘅產品，連基本嘅 share button 都冇，等於自斷生路。如果喺 Instagram / Threads 用一句說話推薦呢個網站，而家根本講唔出一句完整嘅 share link——因為冇。  
\- \*\*具體改法\*\*：每節練習結束後加「分享成績俾同學」按鈕（生成帶成績嘅圖片 \+ 網站 link）。首頁加 social proof（「已有 X 名學生使用」）。加 Instagram / Threads 連結喺 footer。加 Web Share API 支援手機原生分享。

\*\*致命問題 2：題目未經人手覆核就上線\*\*  
\- \*\*具體現象\*\*：全站 26,497 條題目，透明度頁面明確寫「題目經自動檢查上線，未經逐題人手覆核」。解析由 AI 生成，只通過「術語同書面語檢查、結構同難度比例驗證、格式閘」三道自動化檢查。  
\- \*\*對用戶嘅影響\*\*：學生可能會遇到 AI 生成嘅錯誤答案或誤導性解析，直接影響學習效果同考試成績。一旦學生發現一條錯題，就會對全站 26,497 條題目嘅可信度產生懷疑。  
\- \*\*點解不可接受\*\*：DSE 係影響學生一生嘅考試，一條錯誤嘅解析可能令學生學錯一個概念，喺考場上失分。AI 生成嘅教育內容未經人手覆核就上線，喺教育領域係不可接受嘅風險。  
\- \*\*具體改法\*\*：每條題目加顯眼嘅「未經人手覆核」標籤（而家只有小字「經自動檢查」）。優先覆核熱門科目（數學、物理、化學、生物、英文、中文）嘅題目。設立「社群驗題」機制，讓學生可以投票確認題目正確性。每條題目嘅解析底部加「呢條題目有 X 人確認無誤」嘅 counter。

\*\*致命問題 3：答錯後嘅解析預設收起\*\*  
\- \*\*具體現象\*\*：答錯後，解析預設只顯示一句「正解思路：設垂直牆的兩邊各長 x，平行牆的一邊 \= 40 − 2x。」，要撳「睇埋成個解析」先睇到完整推導。仲要喺完成錯因選擇 \+ 情緒彈窗之後先可以撳。  
\- \*\*對用戶嘅影響\*\*：學生答錯題後最迫切嘅需求係即刻睇到完整解析，但而家要經歷 3 步摩擦（揀錯因 → 略過情緒彈窗 → 撳展開解析）。中六生時間寶貴，呢個 flow 會令佢哋直接略過解析。  
\- \*\*點解不可接受\*\*：網站嘅核心理念係「掌握邏輯」，但解析——邏輯嘅載體——卻被三重關卡收埋。呢個同產品嘅核心價值直接矛盾。  
\- \*\*具體改法\*\*：答錯後即刻顯示完整解析（唔收起）。錯因選擇改為解析底部嘅一個簡單 tag（一撳即記錄，唔彈窗）。情緒記錄移至每節結束時。提供「以後唔好收埋，直接畀我睇晒」嘅設定（而家有，但預設應該係展開）。

\*\*致命問題 4：25 科全部「已上線」但部分科目題目質素存疑\*\*  
\- \*\*具體現象\*\*：25 個科目全部標示「已上線」，每科約 866-1624 條 MC。但音樂、體育、視藝、科技與生活等科目嘅 DSE 考核形式主要係實作/創作/聆聽，MC 練習對呢啲科目嘅實際幫助極低。呢啲科目每科只有 13 條書寫題。  
\- \*\*對用戶嘅影響\*\*：學生揀咗「音樂」以為有 useful 練習，發現淨係得 1014 條 MC 關於「聆聽、創作、演奏知識」——但 DSE 音樂考試嘅核心係演奏同創作，MC 幫唔到。學生會覺得被呃。  
\- \*\*點解不可接受\*\*：將對 DSE 幫助極低嘅科目同核心科目（數學、物理、化學）並列，全部標「已上線」，係誤導。學生唔知道 MC 練習對唔同科目嘅實際價值差異極大。  
\- \*\*具體改法\*\*：每個科目卡片加「MC 練習對本科嘅幫助程度」標籤（高/中/低）。對於音樂、體育、視藝等實作科目，明確標示「MC 練習僅覆蓋筆試部分，實作/創作/演奏需另行準備」。或者將呢啲科目分組為「筆試為主」同「實作為主」。

\*\*致命問題 5：練習頁題目語言混雜問題\*\*  
\- \*\*具體現象\*\*：數學科題目用口語化廣東話（「靠住一幅直牆」「靠牆一邊不需圍欄」），但 DSE 數學卷嘅實際題目係用標準書面語。中文科、英文科嘅題目同樣存在口語化問題。  
\- \*\*對用戶嘅影響\*\*：學生習慣咗口語化嘅題目表述後，喺實際 DSE 考試中可能對正式書面語嘅題目表述感到陌生。  
\- \*\*點解不可接受\*\*：DSE 係正式考試，題目用標準書面語。練習平台嘅題目語言應該貼近真實考試，唔係用口語化嚟「親切」。  
\- \*\*具體改法\*\*：題目正文改為標準書面語。解析同 UI 文案可以保留口語化（親切感），但題目本身必須貼近 DSE 真實表述。

\*\*致命問題 6：首頁信息密度過低，滾動疲勞\*\*  
\- \*\*具體現象\*\*：首頁喺 1920px desktop 上頁面高度 5419px，要滾動約 6 屏先睇晒。Hero section 之後嘅每個 section（盲測 demo、methodology demo、stats、free rationale、subject grid、CTA）都獨佔一整屏，內容稀疏。  
\- \*\*對用戶嘅影響\*\*：學生要不停滾動先搵到自己想要嘅內容，注意力被稀釋。  
\- \*\*點解不可接受\*\*：首頁應該喺 2-3 屏內傳遞核心價值並引導到練習，而唔係用 6 屏慢慢講。  
\- \*\*具體改法\*\*：將盲測 demo、methodology demo、stats 合併為一個互動式 section。Free rationale 收為 hero 下方嘅一行。Subject grid 壓縮為可展開嘅 compact grid。目標：3 屏以內完成「認知 → 信任 → 行動」。

\#\# 4\. 按審視維度嘅詳細批評

\#\#\# 4.1 價值主張與首頁說服力

\*\*批評 1：「掌握邏輯 唔係背答案」太抽象\*\*  
\- \*\*具體現象\*\*：Hero headline 係「掌握邏輯 / 唔係背答案」，副標「無論數字點變，你都識答。DSE 戰場上，你唔係一個人。」  
\- \*\*對用戶嘅影響\*\*：中四學生睇到呢句，佢知你講咩？佢唔知「掌握邏輯」具體係咩。佢只係見到一個 marketing slogan。  
\- \*\*點解不可接受\*\*：價值主張必須具體到令學生即刻 understand「哦，原來係咁」。  
\- \*\*具體改法\*\*：改為「DSE 嘅題目，數字會變，但考法唔變。我哋幫你睇穿考法，唔使背 26,000 條答案。」+ 即刻展示一個 live demo（唔使滾動）。

\*\*批評 2：「DSE 戰場上，你唔係一個人」係廢話\*\*  
\- \*\*具體現象\*\*：副標題包含「DSE 戰場上，你唔係一個人」，但平台冇任何社群功能（社群安全頁明確寫「冇訊息、冇留言、冇心心」）。  
\- \*\*對用戶嘅影響\*\*：學生見到「你唔係一個人」會期待社群功能，發現冇，會覺得被呃。  
\- \*\*點解不可接受\*\*：Marketing slogan 同產品實際功能矛盾。  
\- \*\*具體改法\*\*：刪除「你唔係一個人」，改為「10 分鐘，10 條題，即刻開始」。或者如果真係想強調陪伴感，就加一個輕量級嘅「今日有 X 人一齊練習」counter。

\*\*批評 3：首頁 CTA 唔夠 sharp\*\*  
\- \*\*具體現象\*\*：首頁有兩個 CTA：「揀一科，即刻開始 10 題」嘅 4 個科目按鈕，同底部嘅「開始練習」。但「開始練習」跳轉到 \`/start\` 頁面，嗰度只顯示「揀科目」——又一個選擇頁面。  
\- \*\*對用戶嘅影響\*\*：學生撳「開始練習」後要再揀科目，多一步摩擦。  
\- \*\*點解不可接受\*\*：CTA 應該直接帶學生去做題，唔係帶佢去另一個選擇頁。  
\- \*\*具體改法\*\*：底部 CTA 改為「揀一科即刻開始」+ 直接顯示 4 個科目按鈕（同 hero 一樣），唔好跳轉到 \`/start\`。

\*\*批評 4：首頁底部嘅「點解完全免費」section 太長太抽象\*\*  
\- \*\*具體現象\*\*：「攞分嘅真功夫，唔應該被任何一道牆擋住」+ 三個卡片（高效/公平/利他），每個卡片一段文字。  
\- \*\*對用戶嘅影響\*\*：學生唔需要被說服「免費係好嘅」，佢哋只需要知道「免費、無廣告、唔使登入」。  
\- \*\*點解不可接受\*\*：呢個 section 係自說自話嘅品牌宣言，唔係學生需要嘅資訊。  
\- \*\*具體改法\*\*：壓縮為 hero 下方一行：「免費 · 無廣告 · 唔使登入 · 由 DSE 舊生製作」。刪除整個「點解完全免費」section。

\#\#\# 4.2 資訊架構與導航

\*\*批評 1：「不考之地」命名令人困惑\*\*  
\- \*\*具體現象\*\*：Sidebar 同 footer 都有「不考之地」連結，但名稱唔清楚係咩。點入去發現係「純粹為樂趣而學」嘅內容（廣東話、冷知識等），同 DSE 練習完全無關。  
\- \*\*對用戶嘅影響\*\*：學生喺 sidebar 見到「不考之地」會好奇點入去，發現同溫習無關，覺得浪費時間。  
\- \*\*點解不可接受\*\*：導航命名應該 self-explanatory，唔需要猜。  
\- \*\*具體改法\*\*：改名為「趣味學習」或者「課外天地」，或者移出 sidebar，收埋喺 footer。

\*\*批評 2：「呼吸空間」喺 sidebar 嘅「休息」分類下，但練習頁都有「休息吓」按鈕\*\*  
\- \*\*具體現象\*\*：Sidebar 有「呼吸空間」單獨一頁，但練習頁都有「休息吓」按鈕。兩者嘅關係唔清楚——「休息吓」係跳到呼吸空間定係做咩？  
\- \*\*對用戶嘅影響\*\*：功能重疊令學生困惑。  
\- \*\*點解不可接受\*\*：導航應該清晰，唔應該有兩個入口做同一件事但命名唔同。  
\- \*\*具體改法\*\*：統一命名為「休息」，練習頁嘅「休息吓」直接跳到呼吸空間。

\*\*批評 3：Footer 連結過多且分類混亂\*\*  
\- \*\*具體現象\*\*：Footer 有「關於我們、無障礙設定、信任中心、透明度、私隱政策、社群安全、練習表現點計、聯絡我們」8 個連結，加上「練習、數學、列印練習卷、方法論、呼吸空間」等。  
\- \*\*對用戶嘅影響\*\*：學生喺 footer 搵嘢要掃描 13+ 個連結。  
\- \*\*點解不可接受\*\*：Footer 應該簡潔，法律頁面收埋喺一個「法律與政策」dropdown。  
\- \*\*具體改法\*\*：Footer 簡化為 3 組：練習（科目列表 link）、關於（關於我們、方法論）、政策（dropdown 包含私隱、社群安全、透明度等）。

\*\*批評 4：「我的進度」、「錯誤模式」、「練習表現」三個分析頁面功能重疊\*\*  
\- \*\*具體現象\*\*：Sidebar「分析」下有三個連結：我的進度（dashboard）、錯誤模式（dashboard\#error-dna）、練習表現（predictor）。但「我的進度」頁面空白（未有練習記錄），「錯誤模式」係 dashboard 嘅一個 anchor，「練習表現」係獨立頁面。  
\- \*\*對用戶嘅影響\*\*：學生唔知道三個分析工具嘅區別，要逐個點入去試。  
\- \*\*點解不可接受\*\*：分析功能應該整合為一個 dashboard，唔係拆成三個入口。  
\- \*\*具體改法\*\*：合併為一個「我的數據」頁面，內含 tabs：進度總覽、錯誤模式、練習表現估算。

\#\#\# 4.3 內容質量與可信度

\*\*批評 1：解析質素參差——數學科解析算合格，但文科科目存疑\*\*  
\- \*\*具體現象\*\*：數學科嘅解析（圍欄求最大面積）包含完整推導（設 x → 面積函數 → 頂點公式 → 答案）、常見陷阱解釋、Casio 計算機提示。質素算唔錯。但英文、中文、歷史等文科科目嘅解析我無法逐一驗證，考慮到全部未經人手覆核，存疑。  
\- \*\*對用戶嘅影響\*\*：數學科學生可以放心參考，但文科科目嘅解析可能存在概念性錯誤。  
\- \*\*點解不可接受\*\*：教育產品嘅可信度係 all-or-nothing。一條錯誤解析就足以摧毁整個平台嘅信任。  
\- \*\*具體改法\*\*：為每科建立「覆核進度」指標（例如「數學：已覆核 45%」「化學：已覆核 12%」），讓學生知道邊科可信。優先覆核熱門科目。

\*\*批評 2：盲測黑題 demo 嘅數字用中文寫（「五十°」「六十五°」）影響可讀性\*\*  
\- \*\*具體現象\*\*：首頁盲測黑題 demo 嘅選項用中文數字（A 六十五°、B 五十°、C 一三〇°、D 二十五°），而練習頁用阿拉伯數字（A 100 平方米、B 200 平方米）。  
\- \*\*對用戶嘅影響\*\*：學生要額外花時間將中文數字轉換為阿拉伯數字，喺考試中浪費時間。  
\- \*\*點解不可接受\*\*：DSE 數學卷嘅選項用阿拉伯數字，練習平台應該貼近真實考試格式。  
\- \*\*具體改法\*\*：盲測 demo 嘅選項改為阿拉伯數字（A 65°、B 50°、C 130°、D 25°）。或者如果盲測嘅目的係「隱藏具體數字」，用「XX°」格式更合理。

\*\*批評 3：方法論頁面嘅 4 個框架太抽象，缺乏具體 DSE 例子\*\*  
\- \*\*具體現象\*\*：方法論頁展示 4 個核心框架（轉化思維、變化率直覺、條件分解、建模能力），但每個框架只有一個簡單例子（二次方程、化學反應速率等），冇對照真實 DSE past paper 題型。  
\- \*\*對用戶嘅影響\*\*：學生睇完仍然唔知道呢 4 個框架具體點樣對應 DSE 考題。  
\- \*\*點解不可接受\*\*：方法論應該用具體 DSE 題目類型嚟說明，唔係用抽象概念。  
\- \*\*具體改法\*\*：每個框架加 2-3 個真實 DSE 題型例子（例如「轉化思維」→ DSE 2019 數學卷 II Q14、DSE 2022 物理 MC Q8）。

\*\*批評 4：「未經人手覆核」嘅披露不夠顯眼\*\*  
\- \*\*具體現象\*\*：首頁底部有小字「題目經自動檢查上線，未經逐題人手覆核」，但字級極細，喺手機上幾乎睇唔到。練習頁嘅「經自動檢查」標籤同樣唔顯眼。  
\- \*\*對用戶嘅影響\*\*：學生可能冇注意到呢個重要披露，誤以為題目經過專業教師審核。  
\- \*\*點解不可接受\*\*：呢個係影響信任嘅關鍵資訊，應該顯眼但唔嚇人。  
\- \*\*具體改法\*\*：首頁嘅披露改為正常字級嘅 info box（黃色背景），明確寫「AI 生成 \+ 自動檢查，未經人手覆核。發現錯誤請舉報」。練習頁同樣加 info badge。

\#\#\# 4.4 交互設計與使用流程

\*\*批評 1：由進入網站到完成一題有效練習嘅步驟過多\*\*  
\- \*\*具體現象\*\*：首頁 → 撳科目 → 等待題目載入（有 loading skeleton）→ 讀題 → 揀答案 → 揀錯因 → 略過情緒彈窗 → 撳展開解析 → 先睇到完整解析。至少 7 步。  
\- \*\*對用戶嘅影響\*\*：每一步都有流失。中六生時間有限，步驟越多，完成率越低。  
\- \*\*點解不可接受\*\*：理想流程應該係：首頁 → 撳科目 → 讀題 → 揀答案 → 即刻睇到完整解析。4 步。  
\- \*\*具體改法\*\*：去掉錯因選擇彈窗（改為解析底部嘅 tag）。去掉情緒彈窗（移至節末）。解析預設展開。

\*\*批評 2：練習頁載入時顯示 skeleton loader 但無進度指示\*\*  
\- \*\*具體現象\*\*：進入練習頁時，畫面顯示 skeleton placeholder（灰色閃爍條），但冇 loading spinner 或者文字提示「載入中...」。載入時間約 3-5 秒。  
\- \*\*對用戶嘅影響\*\*：學生唔知道係咪載入緊定係出咗錯，可能會撳多幾次或者直接離開。  
\- \*\*點解不可接受\*\*：Loading state 必須有明確嘅文字提示。  
\- \*\*具體改法\*\*：Skeleton loader 下方加「正在準備你嘅 10 條練習題...」文字。或者用進度條。

\*\*批評 3：「今日夠了」按鈕命名令人不安\*\*  
\- \*\*具體現象\*\*：練習頁頂部有「今日夠了」按鈕，撳咗會結束當節練習。  
\- \*\*對用戶嘅影響\*\*：對中六生嚟講，「今日夠了」聽落似放棄，會令學生有負面情緒。  
\- \*\*點解不可接受\*\*：UX 文案應該鼓勵性但唔強迫。「今日夠了」嘅語氣暗示學生偷懶。  
\- \*\*具體改法\*\*：改為「今日收工」或者「先做到呢度」，語氣中性啲。

\*\*批評 4：空狀態處理唔一致\*\*  
\- \*\*具體現象\*\*：Dashboard 頁面嘅空狀態（未有練習記錄）處理得好（有鼓勵性文案 \+ CTA）。但 Predictor 頁面嘅空狀態只有「仲未有練習紀錄」一句，冇 CTA 引導。Bookmarks 頁面未有內容時嘅空狀態未知。  
\- \*\*對用戶嘅影響\*\*：學生喺 predictor 頁面見到空白，唔知道下一步做咩。  
\- \*\*點解不可接受\*\*：所有空狀態都應該有引導性 CTA。  
\- \*\*具體改法\*\*：Predictor 空狀態加「開始第一節練習」按鈕，同 Dashboard 一致。

\*\*批評 5：「下一題想要：跟我節奏 / 基礎 / 進階 / 再深入啲」功能意義唔明\*\*  
\- \*\*具體現象\*\*：每題答完後底部有 4 個難度選項。但「跟我節奏」同其他三個唔係同一維度——前兩個係自適應指令，後兩個係難度選擇。  
\- \*\*對用戶嘅影響\*\*：學生唔知道「跟我節奏」係咩意思，可能唔會撳。  
\- \*\*點解不可接受\*\*：選項應該係同一維度、互斥嘅。  
\- \*\*具體改法\*\*：改為 3 個難度選項（基礎 / 跟我節奏 / 進階），「再深入啲」改為解析底部嘅「想睇更多」連結。

\#\#\# 4.5 視覺設計與品牌感

\*\*批評 1：暗色主題嘅對比度不足\*\*  
\- \*\*具體現象\*\*：背景 \`rgb(26, 25, 23)\`（深炭灰），正文 \`rgb(240, 232, 220)\`（暖白），但次要文字（footer 免責聲明、sidebar 底部 quote）嘅對比度偏低，估計約 4:1-5:1，可能唔達 WCAG AA 標準。  
\- \*\*對用戶嘅影響\*\*：喺光線充足嘅環境下，次要文字難以閱讀。  
\- \*\*點解不可接受\*\*：教育產品必須符合 WCAG AA 對比度標準（4.5:1）。  
\- \*\*具體改法\*\*：次要文字顏色由目前嘅暖灰改為更亮嘅 \`rgb(200, 192, 180)\`，確保對比度 ≥4.5:1。

\*\*批評 2：Owl mascot 風格唔統一\*\*  
\- \*\*具體現象\*\*：首頁 hero 嘅 owl 係 3D 渲染風格（beige 色、坐喺書上面），Dashboard 頁嘅 owl 係另一個 pose（綠色 hoodie、揸住杯），Sidebar 嘅 owl 又係另一個風格（簡化 icon）。  
\- \*\*對用戶嘅影響\*\*：品牌形象唔統一，感覺似拼湊。  
\- \*\*點解不可接受\*\*：品牌 mascot 應該有一致嘅視覺語言。  
\- \*\*具體改法\*\*：統一為同一套 illustration system。如果預算有限，用同一個 owl 嘅不同 pose 但保持相同嘅色彩同風格。

\*\*批評 3：科目圖標用 emoji 唔夠專業\*\*  
\- \*\*具體現象\*\*：25 個科目用 emoji 作為圖標（🔢 數學、⚡ 物理、⚗️ 化學、🧬 生物等）。  
\- \*\*對用戶嘅影響\*\*：Emoji 喺不同 OS 上渲染唔同（Apple emoji vs Windows emoji），而且 emoji 令品牌感覺唔夠專業、似玩下。  
\- \*\*點解不可接受\*\*：一個要令學生長期信任嘅教育平台，用 emoji 做科目圖標太隨便。  
\- \*\*具體改法\*\*：設計自訂 SVG icons，每科一個簡潔嘅 line icon。保持視覺一致性。

\*\*批評 4：按鈕風格唔統一\*\*  
\- \*\*具體現象\*\*：首頁有綠色 pill button（開始練習）、淺綠色 rounded button（科目快速按鈕）、文字 link（揀其他科目）、outline button（睇吓點運作）。Dashboard 有綠色 CTA、灰色 secondary button。風格太多。  
\- \*\*對用戶嘅影響\*\*：視覺層級唔清晰，學生唔知邊個係主要 action。  
\- \*\*點解不可接受\*\*：Button hierarchy 應該清晰：primary（綠色實心）、secondary（綠色 outline）、tertiary（文字 link）。  
\- \*\*具體改法\*\*：制定 button design system：Primary \= 綠色實心圓角；Secondary \= 綠色 outline；Tertiary \= 文字 link 帶箭嘴。全局統一。

\*\*批評 5：「Study Smarter, Not Harder」英文 tagline 喺粵語平台格格不入\*\*  
\- \*\*具體現象\*\*：Sidebar logo 下方顯示「Study Smarter, Not Harder」，但全站主要語言係粵語 \+ 書面語。  
\- \*\*對用戶嘅影響\*\*：英文 tagline 令品牌定位模糊——係英文平台定中文平台？  
\- \*\*點解不可接受\*\*：品牌語言應該一致。如果目標用戶係 DSE 考生，tagline 應該用中文。  
\- \*\*具體改法\*\*：改為粵語 tagline，例如「溫得精，唔使死操」或者保留英文但改為更簡潔嘅「Smart Practice」。

\#\#\# 4.6 性能、穩定性與技術細節

\*\*批評 1：練習頁載入速度偏慢\*\*  
\- \*\*具體現象\*\*：從首頁撳科目到練習題顯示，需要約 3-5 秒，期間顯示 skeleton loader。  
\- \*\*對用戶嘅影響\*\*：中六生喺小息 10 分鐘內想做幾題，3-5 秒嘅載入已經佔用咗寶貴時間。  
\- \*\*點解不可接受\*\*：練習題應該喺 1 秒內載入。  
\- \*\*具體改法\*\*：用 Static Generation（SSG）預渲染題目，或者用 Service Worker cache 題目數據。將題目 JSON 放喺 CDN edge。

\*\*批評 2：無 analytics 追蹤，無法量化問題\*\*  
\- \*\*具體現象\*\*：私隱政策明確寫「全站冇任何分析服務、冇廣告網絡、冇追蹤像素」。呢個對私隱好，但產品團隊完全睇唔到用戶行為數據。  
\- \*\*對用戶嘅影響\*\*：產品團隊無法知道學生喺邊度流失、邊啲題目最常答錯、邊個頁面最多人訪問。  
\- \*\*點解不可接受\*\*：一個要成為「溫習神器」嘅產品，必須有數據驅動嘅迭代。零 analytics 等於盲飛。  
\- \*\*具體改法\*\*：加 privacy-friendly analytics（Plausible 或 Umami，self-hosted），只追蹤 page views 同事件，唔追蹤個人身份。喺私隱政策更新。

\*\*批評 3：圖片數量少但 owl 圖片冇用 next/image 優化\*\*  
\- \*\*具體現象\*\*：首頁 owl 圖片用 \`\_next/image\` 但 \`loading: "auto"\`（冇 lazy load），喺首屏就載入。圖片尺寸 176x142，應該好細但用咗 Next.js Image 組件。  
\- \*\*對用戶嘅影響\*\*：首屏載入可能因為 owl 圖片而延遲。  
\- \*\*點解不可接受\*\*：首屏圖片應該用 \`priority\` 而唔係 \`auto\`。  
\- \*\*具體改法\*\*：owl 圖片加 \`priority\` 屬性。其他圖片全部 \`loading: "lazy"\`。

\*\*批評 4：PWA 安裝提示時機不對\*\*  
\- \*\*具體現象\*\*：學生第一次打開網站就顯示「加到主畫面」橫幅，但 PWA 嘅 \`beforeinstallprompt\` event 應該喺用戶有互動後先觸發。  
\- \*\*對用戶嘅影響\*\*：首次訪問就彈出安裝提示，令學生覺得被打擾。  
\- \*\*點解不可接受\*\*：PWA 安裝提示嘅最佳實踐係喺用戶完成核心任務後先顯示。  
\- \*\*具體改法\*\*：用 \`beforeinstallprompt\` event，喺學生完成第一節練習後先顯示安裝提示。

\#\#\# 4.7 增長機制與分享動力

\*\*批評 1：零分享機制——呢個係致命嘅\*\*  
\- \*\*具體現象\*\*：全站冇 share button、冇 social media link、冇 referral mechanism、冇 invite friend 功能。學生就算覺得好用，都冇便捷方式分享俾同學。  
\- \*\*對用戶嘅影響\*\*：產品完全依賴自然口碑，但冇播種。  
\- \*\*點解不可接受\*\*：一個以口碑為增長策略嘅產品，連 share button 都冇，等於自斷生路。  
\- \*\*具體改法\*\*：每節練習結束後加「分享俾同學」按鈕，生成成績圖片 \+ 網站 link。首頁加 social proof。Footer 加 Instagram / Threads 連結。加 Web Share API。加「邀請同學一齊練」功能（生成專屬 link，睇到邊個朋友都喺度練）。

\*\*批評 2：冇「今日挑戰」或者每日 streak 機制\*\*  
\- \*\*具體現象\*\*：Dashboard 有「今日肯打開嚟已經好叻」嘅鼓勵文案，但冇 streak 機制、冇每日挑戰、冇 leaderboard。  
\- \*\*對用戶嘅影響\*\*：學生缺乏每日返嚟練習嘅動力。  
\- \*\*點解不可接受\*\*：一個要成為「日常溫習工具」嘅產品，需要 retention mechanism。  
\- \*\*具體改法\*\*：加「每日 10 題挑戰」（完成後生成可分享嘅成績卡）。加 streak counter（連續練習日數）。加「同班朋友排行榜」（opt-in）。

\*\*批評 3：如果喺 Instagram / Threads 用一句說話推薦，講唔出\*\*  
\- \*\*具體現象\*\*：如果我要喺 Instagram 推薦呢個網站，我會寫：「免費 DSE 練習平台，25 科 26,000 條 MC，AI 生成但未經人手覆核，掌握邏輯唔係背答案。」——但呢句太長太模糊，而且「AI 生成但未經人手覆核」會令聽眾卻步。  
\- \*\*對用戶嘅影響\*\*：學生唔知道點樣用一句說話向同學推薦。  
\- \*\*點解不可接受\*\*：產品需要一個 elevator pitch。  
\- \*\*具體改法\*\*：提煉一句 elevator pitch：「DSE 25 科免費 MC 練習，答錯即刻拆解你嘅錯因，10 分鐘 10 題，唔使登入。」加喺首頁 hero 下方 \+ share 功能。

\*\*批評 4：冇 SEO landing pages 針對具體科目\*\*  
\- \*\*具體現象\*\*：Subjects 頁面係一個統一嘅列表，冇針對「DSE 數學練習」「DSE 物理練習」等搜尋意圖嘅獨立 landing pages。  
\- \*\*對用戶嘅影響\*\*：學生喺 Google 搜「DSE 數學練習」可能搵唔到呢個網站。  
\- \*\*點解不可接受\*\*：有機搜尋係免費增長渠道。  
\- \*\*具體改法\*\*：為每科建立獨立 landing page（\`/subjects/math\` 已有，但需要加 SEO-optimized content：科目介紹、題型分析、DSE 考核重點、免費練習 CTA）。

\#\#\# 4.8 風險與合規

\*\*批評 1：AI 生成教育內容嘅法律風險\*\*  
\- \*\*具體現象\*\*：26,497 條題目由 AI 生成，未經人手覆核。如果某條題目嘅答案或解析有錯誤，令學生學錯概念並喺 DSE 考試中失分，理論上存在法律索償風險。  
\- \*\*對用戶嘅影響\*\*：學生可能因為信任平台嘅錯誤解析而影響考試成績。  
\- \*\*點解不可接受\*\*：免責聲明雖然寫咗「僅供參考」，但教育產品有更高嘅注意義務。  
\- \*\*具體改法\*\*：每條題目加顯眼嘅「AI 生成，未經人手覆核」免責標籤。加快人手覆核進度。考慮購買專業責任保險。

\*\*批評 2：版權風險低但需持續監控\*\*  
\- \*\*具體現象\*\*：透明度頁面明確寫「全部都係原創改寫」，免責聲明寫「並非 HKEAA 官方試題」。呢個做法版權風險低。但如果 AI 生成過程中訓練數據包含 HKEAA 官方試題，改寫後可能仍有實質相似性。  
\- \*\*對用戶嘅影響\*\*：如果 HKEAA 提出版權挑戰，平台可能需要下架部分題目。  
\- \*\*點解不可接受\*\*：版權訴訟成本高，對非營利項目係致命打擊。  
\- \*\*具體改法\*\*：定期比對題目同 HKEAA 官方試題嘅相似度。保留 AI 生成過程嘅文檔記錄，證明原創性。

\*\*批評 3：Google 登入收集學生選項數據，私隱政策需更透明\*\*  
\- \*\*具體現象\*\*：私隱政策寫「每題你揀咗邊個選項」會上傳到伺服器，用於跨裝置同步。呢個意味住平台伺服器存有學生每題嘅具體答案。  
\- \*\*對用戶嘅影響\*\*：學生可能唔知道佢哋嘅每個答案都被上傳。  
\- \*\*點解不可接受\*\*：雖然私隱政策寫得好詳細，但學生好少會讀完。需要喺 Google 登入時彈出簡短同意。  
\- \*\*具體改法\*\*：Google 登入時加一個簡短嘅同意彈窗：「登入後，你嘅練習進度同每題答案會上傳到我哋伺服器（Supabase，東京），用於跨裝置同步。你可以隨時刪除。」

\*\*批評 4：「練習表現估算」可能誤導學生\*\*  
\- \*\*具體現象\*\*：Predictor 頁面提供「練習表現估算」，雖然有多處免責聲明「唔係考評局成績預測」，但學生可能會將呢個數字當真，影響佢哋嘅溫習策略或心理狀態。  
\- \*\*對用戶嘅影響\*\*：學生可能因為估算分數高而鬆懈，或者因為低而氣餒。  
\- \*\*點解不可接受\*\*：對 DSE 考生嘅心理狀態有潛在負面影響。  
\- \*\*具體改法\*\*：估算結果改為範圍（例如「5-6 級」）而唔係單一數字。加更顯眼嘅提醒：「呢個數字只反映你喺本站嘅 MC 表現，唔代表你嘅 DSE 成績。」

\#\# 6\. 如果呢個網站係我嘅，我會點樣由頭重塑

1\. \*\*重新定義價值主張\*\*：改為「DSE 25 科 MC 練習，10 分鐘 10 題，答錯即刻拆解錯因，免費唔使登入」。一句講完，唔抽象。

2\. \*\*首頁改為單屏 hero \+ live demo\*\*：左半屏文案 \+ CTA，右半屏即刻展示一條盲測黑題 demo，學生可以即刻互動。唔使滾動就體驗到核心價值。

3\. \*\*練習流程壓縮到 4 步\*\*：揀科目 → 讀題 → 揀答案 → 即刻睇完整解析。去掉所有彈窗、錯因選擇改為解析底部 tag。

4\. \*\*AI 深度個性化學習路徑\*\*：根據學生嘅錯題模式，AI 即刻生成針對性練習（例如「你喺二次函數最值題連續錯 3 次，呢 5 條題專攻呢個盲點」）。呢個先係 AI 嘅真正價值，唔係淨係出題。

5\. \*\*AI 生成「錯因深度分析報告」\*\*：每節結束後，AI 分析學生嘅錯題模式，生成一份「你嘅 3 個最大盲點 \+ 下一步建議」，而唔係淨係顯示分數。

6\. \*\*社交化學習\*\*：加「同班朋友排行榜」（opt-in），加「每週挑戰」加 streak 機制。學生可以睇到朋友今日做咗幾多題，互相推動。

7\. \*\*分享驅動增長\*\*：每節結束生成一張精美嘅成績卡圖片（「我今日做咗 10 題數學 MC，答啱 8 題，掌握咗二次函數最值嘅邏輯」），一鍵分享到 IG Story / WhatsApp。

8\. \*\*Desktop 專屬體驗\*\*：加 Cmd+K command palette。加 split view（左邊做題，右邊睇解析）。加即時 stats side panel。大螢幕應該提供比手機更強大嘅功能。

9\. \*\*題目質素分層\*\*：每條題目標示覆核狀態（AI 生成 / 自動檢查通過 / 教師覆核 / 社群驗證）。學生知道邊啲可信。優先覆核熱門科目。

10\. \*\*科目定位清晰化\*\*：將科目分為「筆試為主」（數學、物理、化學等，MC 幫助大）同「實作為主」（音樂、體育、視藝等，MC 幫助有限），唔好將佢哋平等展示。

11\. \*\*品牌視覺統一\*\*：一套自訂 illustration system（owl mascot 統一風格）、一套 icon set（唔用 emoji）、一套 button design system、一個明確嘅 color palette。

\*\*現時版本同理想版本之間嘅差距評分：3.5 / 10\*\*

現時版本有清晰嘅理念同唔錯嘅內容基礎（數學科解析質素算合格），但喺執行上——桌面佈局、交互摩擦、增長機制、品牌一致性、題目覆核——差距巨大。最致命嘅係零增長機制同三重答題摩擦。

\*\*我會唔會放心畀自己嘅小朋友 / 親戚用現時版本？\*\*

\*\*唔會。\*\* 唔係因為內容質素差（數學科解析其實唔錯），而係因為 26,497 條 AI 生成題目未經人手覆核，我唔可以確認每條題目嘅答案同解析都正確。如果小朋友因為一條錯誤解析而學錯概念，喺 DSE 考場失分，呢個風險我承擔唔起。等熱門科目覆核到 70% 以上，我先會推薦。

\#\# 7\. 最終審判

\*\*如果而家 DSE 考生要用呢個網站溫習，我點評價？\*\* 數學、物理等理科科目嘅 MC 練習有一定價值，解析質素算合格，但答錯後嘅三重摩擦（揀錯因 → 情緒彈窗 → 展開解析）會浪費學生寶貴時間。26,497 條題目未經人手覆核，學生需要自行判斷每條解析嘅可信度——呢個對中四至中六學生嚟講負擔太重。可以用，但唔可以盲信。

\*\*如果而家我要投資呢個產品，我點評價？\*\* 唔會投。產品有理念但冇增長引擎——零分享機制、零社交功能、零 analytics、零 retention 機制。一個完全依賴自然口碑但連 share button 都冇嘅產品，唔會有有機增長。而且 26,497 條未覆核題目係一個計時炸彈——一個學生喺社交媒體投訴「呢個平台教錯我」，口碑即刻崩塌。投資前需要：加分享功能、加 analytics、覆核至少熱門 6 科嘅題目、修復桌面佈局。

\#\# 重大修正：基於覆核機制真相嘅更新評估

\#\#\# 1.「2026 DSE 考生覆核」唔等於「專業覆核」

我原本假設嘅最壞情況係「AI 生成 \+ 自動檢查，零人手覆核」。而家事實係：\*\*26,497 條題目全部由 2026 DSE 考生覆核\*\*。

呢個睇落比「零人手覆核」好，但喺我嘅標準下，\*\*呢個仲危險\*\*。原因：

\- 2026 DSE 考生即係啱啱考完或緊接考 DSE 嘅學生。佢哋嘅知識水平係「應考者」級別，唔係「教學者」級別。一個啱啱考完 DSE 數學嘅學生，可以判斷一條 MC 嘅答案啱唔啱，但佢唔一定可以判斷 AI 生成嘅解析係咪\*\*教學上正確\*\*——例如解析用咗一個 DSE 課程範圍外嘅方法、或者解析嘅邏輯推導有微妙嘅概念性錯誤，呢啲學生覆核員好可能睇唔出。  
\- 學生覆核員冇教學經驗，唔知道學生常見嘅誤解點係咩、唔知道點樣嘅解析順序最有效。佢哋只能判斷「呢條答案啱唔啱」，唔能判斷「呢條解析會唔會令學生學錯」。  
\- 25 個科目、26,497 條題目——覆核員要覆核自己考緊嘅科目已經勉強，但如果佢覆核嘅科目唔係佢嘅強項（例如一個理科生覆核中史題），質素更無保障。

\*\*修正評分\*\*：我原本嘅「題目未經人手覆核」致命問題需要改寫為——「題目由同儕覆核但未經專業教學覆核，喺 DSE 教育場景下嘅可信度仍然不足」。

\*\*具體改法（更新）\*\*：  
\- 透明度頁面即刻修正措辭：而家寫「未經逐題人手覆核」——呢個係\*\*誤導性準確\*\*。實際情況係「由 2026 DSE 考生逐題覆核，未經註冊教師或考評局相關人士覆核」。學生有權知道覆核者嘅資歷。  
\- 立即招募註冊教師或者補習名師做抽樣覆核——每科抽 5-10% 題目，如果發現錯誤率超過 2%，全科暫停重新覆核。  
\- 每條題目加「覆核者資歷」標籤：例如「DSE 考生覆核」「教師覆核」「社群驗證」。

\#\#\# 2\. 零數據基礎設施——呢個係最致命嘅發現

你話「未整好 Admin 後台，睇唔到 DAU、留存率、完答率」。呢個係我整個審計中最嚴重嘅發現，比所有 UI/UX 問題加埋一齊嚴重。

一個已經上線、已經有真實 DSE 考生使用嘅產品，\*\*完全睇唔到任何用戶行為數據\*\*：

\- 唔知道每日有幾多人用——無法判斷產品係咪喺度增長定停滯。  
\- 唔知道留存率——無法知道學生係咪用完一次就唔返。  
\- 唔知道完答率——10 題練習有幾多學生做到第 10 題？如果只有 20% 完答，你應該即刻知道「我嘅練習流程有問題」。  
\- 私隱政策寫住收集「你開過 app 嘅日期」——但冇 Admin 後台分析呢啲數據，等於收集咗但用唔到。呢個喺私隱角度係不必要嘅數據收集。

\*\*點解呢個係最致命嘅\*\*：冇數據，你唔知道我嘅審計報告入面指出嘅問題（情緒彈窗打斷節奏、解析收起、三重摩擦）係咪真嘅令學生流失。你可能喺度修復緊一個唔存在嘅問題，同時忽略緊一個真正致命嘅問題。你喺盲飛。而 DSE 考生嘅時間被浪費緊，你連佢哋點樣被浪費都唔知。

\*\*具體改法（更新）\*\*：  
\-即刻起用 1-2 日搭建最基本嘅 Admin dashboard：DAU、WAU、MAU、完答率、科目使用分佈、錯誤舉報數量。呢個比任何 UI 改動都優先。  
\- 如果冇時間建 admin，至少用 Supabase 嘅 SQL query 直接查：\`SELECT date\_trunc('day', created\_at), count(distinct user\_id) FROM practice\_sessions GROUP BY 1\`——10 分鐘就出到 DAU。  
\- 加 product analytics（Plausible self-hosted，符合私隱政策），追蹤關鍵事件：\`practice\_started\`、\`question\_answered\`、\`practice\_completed\`、\`explanation\_viewed\`、\`error\_reported\`。

\#\#\# 3\. 零學生反饋——產品團隊同用戶完全斷裂

「冇收集過學生反饋」——一個為 DSE 考生而做嘅產品，從來冇問過 DSE 考生「你覺得點」。

\- 社群安全頁寫「冇訊息、冇留言、冇心心」——呢個係刻意設計，但連最基本嘅反饋渠道都冇，就係另一回事。  
\- 透明度頁寫「發現錯誤？話我哋知」——但淨係一個 email（dselevelup@gmail.com），學生要離開網站、打開 email app、寫 email 先可以畀反饋。摩擦太大。  
\- Instagram 有 DM 互動（「DM 我哋『立意』」）——但網站唔連結 IG，學生根本唔知有呢個渠道。

\*\*具體改法\*\*：  
\- 每節練習結束頁加一個簡單嘅反饋條：「今日嘅練習體驗點？」+ 1-5 星評分 \+ 可選文字反饋。一行 code 就搞掂，但令產品團隊第一次可以聽到用戶嘅聲音。  
\- 練習頁底部加「報告呢條題目嘅問題」按鈕（而家有「呢條題有問題？話我哋知」但係文字 link，太唔顯眼）。改為 icon button \+ 簡短 form。  
\- 用 Google Form 或 Tally 做一次性用戶調查，問 3 條問題：你最常用咩科目？最唔滿意咩？你會推薦俾同學嗎（NPS）？

\#\#\# 4\. 「練習表現估算」無法驗證——可能誤導學生而唔自知

Predictor 頁面提供「練習表現估算」，私隱政策寫「只反映你喺本站嘅練習」。但：

\- 冇 Admin 後台，無法知道幾多學生用咗 predictor。

\*\*具體改法\*\*：

\- 估算結果加置信區間：「基於 X 題 MC，估算範圍：4-6 級（低置信度）」。

\#\# 必須修復嘅漏洞

\#\#\# 漏洞 1：缺少 HSTS 標頭（嚴重）

\*\*具體現象\*\*：HTTP 回應標頭中冇 \`Strict-Transport-Security\`（HSTS）。所有頁面都返回 \`"hsts": "MISSING"\`。

\*\*攻擊方式\*\*：如果學生喺公共 WiFi（咖啡店、港鐵）上用 HTTP 連線（即使最終被重導到 HTTPS），中間人攻擊者可以喺重定向之前截獲請求。冇 HSTS 標頭，瀏覽器唔會強制記住「呢個網站只能用 HTTPS」。

\*\*對用戶嘅影響\*\*：喺公共網絡上使用 DSE Level Up 嘅學生，可能被中間人攻擊截獲 Google 登入 token 或者練習數據。

\*\*點解不可接受\*\*：HSTS 係 HTTPS 網站嘅基本安全標準。冇 HSTS，等於話俀攻擊者知「你可以在第一次請求時攔截」。

\*\*修復方法\*\*：喺 \`next.config.js\`（或 \`next.config.mjs\`）加入：  
\`\`\`js  
const securityHeaders \= \[  
  {  
    key: 'Strict-Transport-Security',  
    value: 'max-age=63072000; includeSubDomains; preload'  
  }  
\];

module.exports \= {  
  async headers() {  
    return \[  
      {  
        source: '/(.\*)',  
        headers: securityHeaders,  
      },  
    \];  
  }  
};  
\`\`\`

\#\#\# 漏洞 2：CSP 允許 \`unsafe-inline\` script（中等）

\*\*具體現象\*\*：Content-Security-Policy 中 \`script-src 'self' 'unsafe-inline'\` 允許內聯腳本執行。\`style-src 'self' 'unsafe-inline'\` 同樣允許內聯樣式。

\*\*攻擊方式\*\*：如果攻擊者搵到任何 XSS 漏洞（即使好細），\`unsafe-inline\` 會令 CSP 無法阻擋惡意腳本執行。

\*\*對用戶嘅影響\*\*：如果未來有 XSS 漏洞被引入（例如新功能嘅輸入冇做好過濾），CSP 唔能夠作為最後防線。

\*\*點解不可接受\*\*：CSP 嘅目的就係作為 XSS 嘅最後防線。\`unsafe-inline\` 令呢個防線形同虛設。

\*\*修復方法\*\*：用 nonce-based CSP 替代 \`unsafe-inline\`。Next.js 支援：  
\`\`\`js  
// next.config.js  
module.exports \= {  
  experimental: {  
    nonce: true,  
  },  
}  
\`\`\`  
然後將 CSP 改為 \`script-src 'self' 'nonce-{random}'\`。不過注意：如果用咗 Tailwind CDN（\`cdn.tailwindcss.com\`），需要將 CDN 加入 \`script-src\`，或者改用本地 Tailwind。

\#\#\# 漏洞 3：Tailwind CSS 從 CDN 載入（中等）

\*\*具體現象\*\*：頁面載入 \`https\://cdn.tailwindcss.com\`——呢個係 Tailwind 嘅 Play CDN，官方明確標示「唔適合生產環境」。

\*\*攻擊方式\*\*：如果 \`cdn.tailwindcss.com\` 被攻擊或者供應鏈被入侵，攻擊者可以注入惡意 JavaScript 到所有 DSE Level Up 頁面。雖然 CSP 限制咗 \`script-src 'self'\`，但 CDN 載入嘅樣式表可能被用於 CSS injection。

\*\*對用戶嘅影響\*\*：供應鏈攻擊風險。

\*\*點解不可接受\*\*：CDN Play 版本有性能問題（client-side JIT compilation）同安全風險。

\*\*修復方法\*\*：改用本地 Tailwind。喺項目入面安裝 \`tailwindcss\` 作為 dev dependency，用 PostCSS 處理。移除 \`\<script src="https\://cdn.tailwindcss.com"\>\`。

\#\#\# 漏洞 4：缺少 Rate Limiting（中等）

\*\*具體現象\*\*：連續發送 5 個請求到 \`/api/auth/providers\`，全部喺 3-4ms 內完成，冇被限流。Vercel 嘅 WAF 阻擋咗明顯嘅攻擊，但對於低速率嘅 brute force 攻擊冇保護。

\*\*攻擊方式\*\*：攻擊者可以低速嘗試暴力破解 Google OAuth callback、嘗試各種 API endpoint、或者做 user enumeration。

\*\*對用戶嘅影響\*\*：DDoS 攻擊可能令網站對真實學生不可用。

\*\*點解不可接受\*\*：對於一個處理未成年人數據嘅教育平台，Rate limiting 係基本保護。

\*\*修復方法\*\*：用 Vercel 嘅 Edge Functions 加 rate limiting，或者用 Upstash Redis 做 token bucket rate limiting。私隱政策已經提到「伺服器會喺記憶體按 IP 位址計算請求次數」——確保呢個功能已經實施並有效。

\#\#\# 漏洞 5：robots.txt 暴露內部路徑結構（低）

\*\*具體現象\*\*：robots.txt 包含 \`Disallow: /admin/\`、\`/account\`、\`/sign-in\`、\`/sign-up\`——呢個等於公開咗呢啲路徑嘅存在。攻擊者讀完 robots.txt 就知道要嘗試攻擊邊啲 endpoint。

\*\*對用戶嘅影響\*\*：為攻擊者提供咗路線圖。

\*\*點解不可接受\*\*：雖然呢啲 endpoint 都有認證保護，但唔應該主動暴露路徑結構。

\*\*修復方法\*\*：robots.txt 嘅 \`Disallow\` 唔應該列出具體路徑。改為只保留 \`Allow: /\` 同 \`Disallow: /api/\`。敏感路徑嘅保護應該靠認證，唔靠 robots.txt 隱藏。

\#\# 安全加固建議（非緊急但建議做）

\#\#\# 建議 1：加 security.txt

\*\*現象\*\*：\`/.well-known/security.txt\` 返回 404。Security researchers 冇正式渠道報告漏洞。

\*\*修復\*\*：喺 \`public/\` 目錄建立 \`.well-known/security.txt\`，內容：  
\`\`\`  
Contact: mailto:dselevelup@gmail.com  
Preferred-Languages: zh-HK, en  
Canonical: https\://dse-level-up-by-claude-code.vercel.app/.well-known/security.txt  
\`\`\`

\#\#\# 建議 2：Google OAuth state validation 加強

\*\*現象\*\*：Auth.js 嘅 Google OAuth 流程已經有 CSRF 保護（state parameter），但 \`/api/auth/providers\` 公開咗完整嘅 OAuth callback URL。

\*\*修復\*\*：確保 \`callbackUrl\` 只接受同源 URL。喺 Auth.js 配置入面加：  
\`\`\`js  
callbacks: {  
  async redirect({ url, baseUrl }) {  
    if (url.startsWith(baseUrl)) return url;  
    return baseUrl;  
  }  
}  
\`\`\`

\#\#\# 建議 3：Supabase RLS 策略審計

\*\*現象\*\*：私隱政策寫「同步嘅資料只有 14 項」，但我無法從客戶端驗證 Supabase 嘅 Row Level Security（RLS）策略是否正確配置。

\*\*修復\*\*：登入 Supabase Dashboard → Authentication → Policies，確認每張表嘅 RLS 都已經啟用，而且 policies 只允許用戶存取自己嘅數據。特別確認：  
\- 用戶唔可以讀取其他用戶嘅 \`user\_id\` 對應嘅行  
\- 寫入操作只允許 \`service\_role\` key，唔允許 \`anon\` key  
\- \`anon\` key 只有讀取題目數據嘅權限

\#\#\# 建議 4：Vercel Access Token 保護

\*\*現象\*\*：網站部署喺 Vercel 嘅預設域（\`dse-level-up-by-claude-code.vercel.app\`），冇自訂域。如果 Vercel Access Token 外洩，攻擊者可以直接修改部署。

\*\*修復\*\*：  
\- 確保 Vercel 嘅 deploy hooks 同 access tokens 定期輪換  
\- 啟用 Vercel 嘅 Deployment Protection（Password Protection 或 Vercel Authentication）  
\- 購買自訂域（\`dselevelup.hk\`），robots.txt 已經提到呢個計劃
