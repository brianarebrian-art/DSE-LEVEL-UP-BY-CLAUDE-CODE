現行 §12 寫住「**機器永不自動入庫**」。呢句而家唔係事實。

| 入庫途徑 | 條數 | 佔比 |

728 條經 `scripts/qbank/auto-promote.mts` 入庫，該腳本檔頭寫明
「機器閘自動入庫通道（**2026-08-22 Yuna 指令**）」，分佈 15 科。

即係話：憲章禁止嘅嘢，五日前已經由 COO 指令開通並執行咗。

## 二、點解【唔】建議拆走真人閘

原本嘅提議係拆走真人審批以加快出題。實測數字唔支持：

| | 條數 |
|---|---:|
| 四科（中／英／數／公社）**未寫出嚟** | **2,866** |
| 等緊真人審批而未上線 | **40** |

拆走真人閘只會解封 40 條。**樽頸係出題，唔係審批。**

而真人閘確實接得住機器接唔住嘅嘢。2026-08-27 當日實例：

| 缺陷 | 機器閘結果 | 邊個捉到 |
|---|---|---|
| `math_p1_11` 幾何配置同答案矛盾（∠TCA 應 124° 唔係 56°）| 20/20 全過 | 逐條驗算 |
| 歷史 38 條有 42 處口語 + 2 處中英夾雜 | 38/38 全過 | `npm run qa` |
| 公社科 40 條有 34 條「答案係最長項」+ 2 條跨庫重複 | 40/40 全過 | 事後機械檢查 |
| 「公共財政」被誤判為術語違規 | **閘自己判錯** | 人手覆核 |

機器閘由頭到尾**唔檢查答案啱唔啱**（`_gate.mjs` 檔頭原文：
"never correctness (生死線)"）。呢個唔係實作偷懶，係機器做唔到。

## 三、建議條文（取代現行 §12）

> ### 12. 生產紀律 —— 兩條入庫通道
>
> 題目入庫有兩條路。**兩條都合法，但披露方式必須唔同。**
>
> **甲、真人審批通道**（`promote-drafts.mjs` → `*-reviewed.ts`）
> ```
> drafts → review-drafts.mjs（機器閘）→ 審批台 → 真人批 → decisions.json（實名）
>        → promote-drafts.mjs → 人手 wire 入 load.ts + index.ts → npm test
> ```
> 只有呢條路出嚟嘅題，檔頭先可以寫「approved question-by-question by a NAMED human」。
> 支援**逐題全審**同**抽樣覆核**兩種模式；抽樣模式下檔頭必須逐字列明
> 真人讀過幾多條、其餘只過咗機器閘，並列出讀過嗰批嘅 id。
>
> **乙、機器閘通道**（`auto-promote.mts` → `*-auto.ts`）
> ```
> drafts → 機器閘（格式／術語／跨庫重複／課題註冊）→ *-auto.ts → wire
> ```
> **絕對禁止**寫任何真人名入 `decisions.json`。冇批過就冇簽名。
> 前端 `QuestionProvenance` 必須照實顯示「本題未有實名逐題審批紀錄」。
> `framework` 標「機器閘放行題」，唔准標「人手核對題」。
>
> **兩條路共通嘅絕對底線：**
> 1. **紀錄必須同實情一致。** 生成檔檔頭唔可以聲稱冇發生過嘅審批。
> 2. **虛擬 persona 唔可以簽名**（`_reviewer-gate.mjs` 以代碼攔截）。
> 3. **機器閘從來唔檢查答案啱唔啱**——呢句必須寫喺每個相關檔頭，
>    唔可以因為通道開放咗就淡化。
> 4. 出題側必須 correct-by-construction（數理科計出嚟）或引可查證原文，
>    唔准靠閘兜底。
>
> **建議比例（非硬性）：** 高風險科目（數學、理科計算題、有唯一正確答案者）
> 走甲；概念題、補底題走乙。每批走乙嘅題目，建議抽 10% 事後覆核，
> 發現系統性問題就整批退回。

## 四、如果仍然決定拆走真人閘

即使拆走，以下三項**唔可以一齊拆**，否則會由「加快」變成「呃人」：

1. 檔頭唔准寫「逐題人手批」——冇批過就唔可以咁寫（§16.C 同一原則）
2. 前端披露唔准熄——學生有權知呢條題冇人審過
3. 「機器唔檢查答案啱唔啱」呢句唔准刪
